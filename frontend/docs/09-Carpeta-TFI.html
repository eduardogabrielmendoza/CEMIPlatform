2. Resumen Ejecutivo y Marco Introductorio

2.1 Resumen ejecutivo

CEMI Sistema Gestor es una aplicación web integral destinada a digitalizar la gestión del Centro Municipal de Idiomas. El proyecto permite centralizar procesos académicos, administrativos, financieros y comunicacionales que, de otro modo, quedarían distribuidos entre planillas, mensajes, registros físicos o herramientas inconexas.

La solución fue diseñada con una arquitectura cliente-servidor, backend Node.js/Express, base de datos MySQL, frontend HTML/CSS/JavaScript y comunicación en tiempo real mediante Socket.IO. Además, integra funcionalidades de seguridad, recuperación de cuenta, privacidad, comprobantes PDF, chat, notificaciones y classroom.

2.2 Breve descripción del proyecto

El sistema administra alumnos, profesores, administradores, cursos, idiomas, niveles, aulas, inscripciones, pagos, calificaciones, asistencias y recursos de aula virtual. También permite que profesores publiquen tareas, anuncios, encuestas y materiales, mientras los alumnos consultan información académica y realizan entregas desde su perfil.

En términos documentales, el proyecto toma como referencia modelos tradicionales de sistemas de gestión comercial, pero adapta sus conceptos al ámbito educativo: las ventas se transforman en pagos de matrícula/cuotas, el stock se transforma en cupos y recursos, los productos se transforman en cursos y materiales, y la caja se interpreta como seguimiento administrativo de pagos.

2.3 Objetivos principales y metodología

  • Digitalizar la gestión académica de un centro municipal de idiomas.
  • Implementar una base de datos relacional normalizada con integridad de datos.
  • Diseñar una API REST que separe lógica de negocio, rutas, middleware y utilidades.
  • Desarrollar una interfaz web responsive para administración, profesores y alumnos.
  • Incorporar seguridad mediante autenticación, roles, JWT y contraseñas cifradas.
  • Aplicar metodología ágil con planificación por fases y sprints.

2.4 Resultados esperados y conclusiones

Se espera que el sistema permita reducir la carga manual, mejorar la calidad de información, agilizar consultas, documentar pagos y centralizar la comunicación educativa. Como conclusión general, CEMI Sistema Gestor demuestra la integración de conocimientos de programación, base de datos, seguridad, despliegue, documentación y experiencia de usuario en un producto funcional y evaluable.

2.5 Introducción

La transformación digital de instituciones educativas municipales exige herramientas que permitan administrar información de forma clara, segura y disponible. Un centro de idiomas trabaja con datos sensibles, calendarios académicos, pagos, docentes, cursos y alumnos. La falta de una plataforma centralizada puede generar pérdidas de tiempo, errores de carga y dificultad para obtener información confiable.

2.6 Contexto y antecedentes del rubro

Si bien el modelo documental original menciona el rubro minorista y los sistemas POS, en CEMI la problemática equivalente se encuentra en la gestión operativa educativa. Al igual que un comercio necesita controlar productos, ventas y stock, un centro de idiomas necesita controlar cursos, inscripciones, pagos, cupos y recursos académicos. La lógica de trazabilidad se mantiene, pero se aplica a un dominio institucional y educativo.

2.7 Justificación académica y profesional

El proyecto se justifica académicamente porque integra programación web, modelado de datos, arquitectura cliente-servidor, seguridad, diseño de interfaces y documentación formal. Profesionalmente, representa una solución real para una institución que necesita mejorar procesos internos y ofrecer una experiencia más ordenada a alumnos y docentes.

2.8 Objetivo general del sistema

Implementar un sistema web integral para el Centro Municipal de Idiomas que centralice la administración académica, financiera y comunicacional, garantizando trazabilidad, seguridad, disponibilidad y facilidad de uso.

2.9 Objetivos específicos de implementación

  • Gestionar personas, usuarios, perfiles y permisos.
  • Administrar alumnos, profesores, cursos, idiomas, niveles y aulas.
  • Controlar inscripciones, cupos y estados académicos.
  • Registrar pagos, conceptos, estados y comprobantes.
  • Implementar classroom con tareas, entregas, anuncios, encuestas y calendario.
  • Permitir comunicación con chat de soporte y notificaciones.
  • Incluir páginas de seguridad, privacidad y recuperación de cuenta.

3. Estado del Arte y Fundamentación Técnica

3.1 Contexto tecnológico actual

Las aplicaciones web de gestión educativa se han consolidado como una alternativa flexible frente a sistemas de escritorio aislados o plataformas externas cerradas. Herramientas como Moodle, Google Classroom y sistemas administrativos SaaS ofrecen soluciones parciales, pero no siempre cubren la combinación específica de gestión académica, pagos, soporte, seguridad y documentación requerida por una institución local.

3.2 Sistemas existentes y enfoques tecnológicos

SaaS

  • Acceso remoto
  • Actualizaciones externas
  • Costos recurrentes
  • Menor control del código

Escritorio

  • Funcionamiento local
  • Dependencia de una PC
  • Dificultad de acceso remoto
  • Escalabilidad limitada

Web modular

  • Multiplataforma
  • Backend y frontend separados
  • Base centralizada
  • Escalable y evaluable

3.3 Modelado de datos y normalización

El proyecto utiliza una base relacional MySQL. La normalización permite representar entidades como personas, usuarios, alumnos, profesores, cursos, inscripciones, pagos, calificaciones, asistencias, tareas y chats sin duplicar información crítica. Este enfoque reduce inconsistencias y facilita consultas cruzadas entre módulos.

3.4 Seguridad en aplicaciones web

La autenticación con JWT permite validar sesiones de usuario sin almacenar credenciales en el cliente. Las contraseñas se protegen con bcrypt, mientras que Helmet, CORS y rate limiting reducen riesgos básicos de exposición. La separación de roles limita acciones sensibles y evita que alumnos o profesores accedan a funciones administrativas no autorizadas.

3.5 Fundamentación del aporte técnico y académico

  • Integra administración académica y classroom en un mismo ecosistema.
  • Aplica arquitectura cliente-servidor con persistencia real.
  • Incluye despliegue en producción y verificación de health check.
  • Documenta requisitos, manuales, plan de trabajo y criterios de aceptación.
  • Adapta modelos de gestión tradicional a una institución educativa municipal.

4. Descripción y Análisis del Proyecto

4.1 Problemática detectada

La gestión manual o fragmentada genera baja trazabilidad, consultas lentas, duplicidad de datos y dependencia de conocimientos personales de quienes administran la información. En CEMI esto afecta inscripciones, pagos, control de cursos, comunicación con alumnos y seguimiento académico.

4.2 Solución propuesta

Se propone una aplicación web modular con frontend estático, backend Express, base MySQL y comunicación en tiempo real. La solución centraliza procesos y permite que cada usuario interactúe con funcionalidades acordes a su rol.

4.4 Análisis del mercado y oportunidad tecnológica

El mercado ofrece plataformas educativas robustas, pero muchas requieren configuración compleja, suscripciones o integración con sistemas externos. CEMI Sistema Gestor aprovecha tecnologías web accesibles para producir una solución propia, adaptable y documentada, con control sobre código, datos y despliegue.

4.5 Diagrama de Entidad-Relación detallado

El modelo entidad-relación se organiza alrededor de personas y usuarios. Desde personas derivan alumnos, profesores y administradores; desde cursos se relacionan idiomas, niveles, aulas, profesores e inscripciones; desde alumnos y cursos se vinculan pagos, calificaciones, asistencias y classroom. Las tablas de chat y notificaciones agregan trazabilidad comunicacional.

4.7 Reglas de negocio

  • Un alumno debe existir antes de inscribirse a un curso.
  • Un curso debe tener idioma, nivel, profesor, aula y cupo definido cuando corresponda.
  • Un pago debe estar asociado a alumno, curso, concepto y medio de pago.
  • Solo usuarios autenticados pueden acceder a paneles privados.
  • Los profesores solo deben operar sobre cursos asignados.
  • Los comprobantes y estados de pago deben preservar trazabilidad.
  • Las publicaciones de classroom deben vincularse a cursos reales.

4.8 Especificación de requisitos

Los requisitos funcionales RF01 a RF10 y no funcionales RNF01 a RNF09 se encuentran detallados en el Anexo TFI. En esta carpeta se sintetiza su propósito: asegurar que el sistema permita gestionar los módulos centrales, responder correctamente a los roles, preservar datos en MySQL y ofrecer una experiencia web estable y responsive.

4.9 Matriz de trazabilidad y restricciones

La trazabilidad conecta historias de usuario con reglas de negocio y requisitos. Las principales restricciones son: disponibilidad de Internet, uso de navegador moderno, configuración correcta de variables de entorno, carga responsable de datos por administración y capacitación básica a usuarios.

4.10 Mejoras a futuro y escalabilidad

  • Reportes analíticos avanzados.
  • Integración bancaria o conciliación automática.
  • Aplicación móvil nativa.
  • Panel de auditoría extendido.
  • Gestión avanzada de becas, descuentos o planes de pago.

5. Metodología y Desarrollo Técnico

5.1 Enfoque metodológico

El proyecto se desarrolló con un enfoque ágil, distribuido en sprints y tareas incrementales. Esta metodología permitió comenzar con una base funcional, validar módulos por separado y luego integrar pagos, classroom, chat, seguridad y documentación.

5.2 Técnicas y herramientas utilizadas

ÁreaHerramientasUso
BackendNode.js, Express, MySQL2, JWT, bcryptjs, Socket.IOAPI, seguridad, persistencia y tiempo real.
FrontendHTML5, CSS3, JavaScript, Lucide IconsInterfaz, paneles, páginas públicas y documentación.
Base de datosMySQLModelo relacional y datos persistentes.
ServiciosRailway, Cloudinary, SendGrid/NodemailerDeploy, archivos y correo.

5.3 Diseño de arquitectura

Cliente: páginas HTML, CSS y JavaScript servidas desde frontend.

Servidor: Express con rutas por dominio: auth, alumnos, profesores, cursos, pagos, classroom, chat, seguridad, comunidad y estado.

Base de datos: MySQL con relaciones académicas, financieras y comunicacionales.

5.4 Desarrollo e implementación por capas

La capa de presentación contiene páginas públicas, dashboards, perfiles, classroom, seguridad y documentación. La capa de aplicación contiene rutas, middleware, validaciones y lógica de negocio. La capa de datos contiene tablas relacionales, migraciones y consultas mediante el pool de conexión.

5.5 Gestión de base de datos y consistencia

La consistencia se logra vinculando entidades mediante claves y relaciones lógicas. Los pagos se asocian a alumnos y cursos; las inscripciones vinculan alumnos con cursos; las calificaciones y asistencias dependen de alumno y curso; classroom se organiza alrededor de cursos y profesores; y las notificaciones se relacionan con usuarios.

5.6 Gestión de versiones y trabajo colaborativo

Git y GitHub permiten conservar historial de cambios, coordinar avances y desplegar nuevas versiones. El deploy automático en Railway facilita validar el sistema en un entorno público.

5.7 Pruebas, integración y seguridad

  • Validación de sintaxis de servidor y scripts principales.
  • Pruebas de rutas y health check.
  • Validación de navegación entre documentos.
  • Control de referencias antiguas y recursos inexistentes.
  • Verificación de despliegue en producción.

5.8 Implantación y plan de capacitación

La implantación se realiza en Railway con variables de entorno y base MySQL. Para capacitación se propone una guía breve por rol: administración aprende altas, pagos y reportes; profesores aprenden classroom, calificaciones y asistencias; alumnos aprenden acceso, tareas, pagos, comunidad y soporte.
