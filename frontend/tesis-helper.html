Panel de Administrador

Control total del sistema — dashboard_admin.html

🎯 Rol y Propósito

El administrador tiene acceso total al sistema. Es quien gestiona todos los recursos de la institución: alumnos, profesores, cursos, pagos, aulas e idiomas. El panel se renderiza como una Single Page Application (SPA) donde cada sección se carga dinámicamente sin recargar la página.

📂 Secciones del Sidebar

El sidebar se organiza en grupos colapsables:

  • Administración General: Cursos, Alumnos, Profesores, Administradores, Aulas, Idiomas
  • Seguridad: Status del sistema, Recuperación de contraseñas, Códigos CEMI
  • Pagos: Gestión completa de cuotas y registros financieros
  • Chat Soporte: Sistema de chat en tiempo real con Socket.IO
  • Ayuda: Centro de documentación integrado

👥 Gestión de Usuarios

  • CRUD completo de alumnos y profesores
  • Asignación de cursos a profesores
  • Inscripción de alumnos a cursos
  • Cambio de credenciales del Classroom
  • Generación de CemiKeys de acceso
  • Gestión de estados (activo/inactivo)

📊 Gestión Académica

  • Creación y edición de cursos
  • Gestión de idiomas con banderas
  • Administración de aulas y capacidades
  • Control de niveles por idioma
  • Ciclo lectivo y estados de cursos
  • Generación de reportes PDF

💬 Chat de Soporte en Tiempo Real

El admin recibe y gestiona conversaciones de soporte mediante Socket.IO. Puede filtrar por estado (pendiente, activa, cerrada, resuelta), responder mensajes en tiempo real, y recibir notificaciones de escritorio.

Usuario envía mensaje → Socket.IO transmite → Admin recibe notificación → Respuesta en tiempo real
Dato clave para la defensa: El Panel Admin usa tablas con paginación slider, filtros avanzados, y acordeones para cursos. Genera PDFs con jsPDF y jsPDF-AutoTable para reportes institucionales.

Panel del Profesor

Gestión de cursos y alumnos asignados — dashboard_profesor.html

🎯 Rol y Propósito

El profesor accede a un panel enfocado en la gestión académica de sus cursos. Puede visualizar sus cursos activos e históricos, cargar calificaciones, registrar asistencias, y comunicarse con soporte.

📂 Secciones Disponibles

  • Mis Cursos: Lista de cursos activos con estadísticas (total cursos, total alumnos, promedio por curso). Incluye tabla de cursos activos e historial de finalizados.
  • Calificaciones: Seleccionar un curso → ver tabla de alumnos → cargar/editar notas (Parcial 1, Parcial 2, Final). Cálculo automático de promedios.
  • Asistencias: Seleccionar un curso → registrar asistencia por fecha con estados (Presente, Ausente, Tarde, Justificado).
  • Mi Perfil: Vista de datos personales (no editables) e información profesional con estadísticas.
  • Classroom: Enlace directo al aula virtual.
  • Chat Soporte: Comunicación con administración vía Socket.IO.

⚙️ Flujo de Carga de Calificaciones

Profesor selecciona curso → GET /api/calificaciones/:id_curso → Renderiza tabla editable → PUT /api/calificaciones → BD actualizada
Dato clave: El profesor NO puede editar datos personales ni inscribir alumnos. Esas acciones están reservadas al administrador. Esta separación de responsabilidades es parte del diseño de seguridad del sistema.

Panel del Alumno

Consulta académica y financiera — dashboard_alumno.html

🎯 Rol y Propósito

El alumno tiene un panel de consulta donde visualiza sus cursos, calificaciones y pagos. No tiene permisos de escritura sobre datos académicos, solo de lectura. Puede acceder al Classroom y comunicarse con soporte.

📂 Secciones Disponibles

  • Mis Cursos: Cursos activos con promedio, estado (Aprobado, Regular, Reprobado, Pendiente), horario, y detalle expandible. Historial de cursos finalizados.
  • Mis Calificaciones: Tabla con Parcial 1, Parcial 2, Final y Promedio por curso. Escala visual de colores según rendimiento.
  • Mis Pagos: Estado financiero con total pagado, total pendiente y cuotas impagas. Desglose por curso con sistema de tickets de pago estilo tarjeta de crédito.
  • Mi Perfil: Datos personales, legajo, y estadísticas de rendimiento.
  • Classroom: Acceso al aula virtual.
  • Chat Soporte: Canal de comunicación con la administración.

📈 Estadísticas del Alumno

  • Cursos Activos (contador)
  • Promedio General (calculado)
  • Cursos Aprobados / Total
  • Total Pagado vs Pendiente
  • Cuotas Impagas (alerta)

🎨 Sistema de Estados Visuales

  • Aprobado: Promedio ≥ 7.0
  • Regular: Promedio 4.0 - 6.9
  • Reprobado: Promedio < 4.0
  • Pendiente: Sin notas
Dato clave: El sistema de pagos incluye tarjetas estilizadas (credit-card.css) que muestran el estado de cada cuota de forma visual e intuitiva, con tickets descargables.

Apartado de Seguridad

Arquitectura completa de protección del sistema

⚠️ Este es el apartado más importante para la defensa. El sistema implementa múltiples capas de seguridad tanto en frontend como en backend.

🔐 1. Sistema de Autenticación

El sistema soporta dos métodos de autenticación:

  • Login tradicional: Usuario + Contraseña → validación contra la BD con bcrypt para hashing.
  • Login por CemiKey: Clave de acceso única en formato XXXX-XXXX-XXXX que identifica al usuario sin necesidad de usuario/contraseña.
// Verificación de contraseña con bcrypt const stored = String(user.password_hash); let ok = false; if (isBcrypt(stored)) ok = bcrypt.compareSync(pw, stored); // En producción NUNCA se permite plaintext else if (ALLOW_PLAINTEXT && !isProd) ok = pw === stored;

🎫 2. JSON Web Tokens (JWT)

Tras la autenticación exitosa, se genera un token JWT que contiene:

  • id_usuario — Identificador único del usuario
  • id_persona — Referencia a datos personales
  • rol — Determina acceso (admin, profesor, alumno)
  • username — Para logging y auditoría
  • id_especifico — ID del rol (id_administrador, id_profesor, o id_alumno)
// authMiddleware.js - Generación y verificación de tokens const JWT_SECRET = process.env.JWT_SECRET; const JWT_EXPIRES_IN = process.env.JWT_EXPIRES_IN || '24h'; export const generarToken = (payload) => { return jwt.sign(payload, JWT_SECRET, { expiresIn: JWT_EXPIRES_IN }); }; export const verificarToken = (req, res, next) => { const token = authHeader.split(' ')[1]; // Bearer TOKEN const decoded = jwt.verify(token, JWT_SECRET); req.user = decoded; next(); };

👮 3. Control de Acceso Basado en Roles (RBAC)

El sistema implementa un middleware verificarRol que restringe rutas según el rol del token:

export const verificarRol = (...rolesPermitidos) => { return (req, res, next) => { const rolNormalizado = req.user.rol?.toLowerCase(); if (!rolesNormalizados.includes(rolNormalizado)) { return res.status(403).json({ message: 'No tienes permisos para esta acción.' }); } next(); }; };

Además, en el frontend, cada dashboard verifica al cargarse:

// Verificación inmediata al cargar la página if (!localStorage.getItem('token')) { window.location.href = 'login.html?session=expired'; }

🪖 4. Helmet.js — Cabeceras HTTP de Seguridad

Se configura helmet con una Content Security Policy (CSP) estricta:

  • defaultSrc: ["'self'"] — Solo permite recursos propios
  • scriptSrc — Solo CDNs aprobados (unpkg, jsdelivr, cdnjs)
  • objectSrc: ["'none'"] — Bloquea plugins (Flash, Java)
  • frameSrc: ["'none'"] — Previene clickjacking

⏱️ 5. Rate Limiting

Protección contra ataques de fuerza bruta y DDoS:

const limiter = rateLimit({ windowMs: 15 * 60 * 1000, // ventana de 15 minutos max: 1000, // máximo 1000 requests por IP message: 'Demasiadas peticiones, intente más tarde.', skip: (req) => req.path.startsWith('/api/chat') // excluir chat });

🌐 6. CORS (Cross-Origin Resource Sharing)

Solo se permiten orígenes registrados explícitamente:

const allowedOrigins = [ 'http://localhost:8080', 'http://localhost:3000', process.env.FRONTEND_URL, process.env.RAILWAY_PUBLIC_DOMAIN ].filter(Boolean);

✅ 7. Validación de Datos (express-validator)

Todas las rutas POST/PUT usan validación de entrada:

  • Sanitización de inputs con trim() y normalizeEmail()
  • Validación de tipos: isEmail(), isLength(), matches()
  • Patrón de username: /^[a-zA-Z0-9_.-]+$/
  • Contraseña mínima: 6 caracteres
  • Protección contra SQL Injection mediante queries parametrizadas

🔑 8. Sistema CemiKey

Cada usuario recibe una clave de acceso única generada con caracteres no ambiguos (sin 0, O, 1, I, L):

const ALLOWED_CHARS = 'ABCDEFGHJKMNPQRSTUVWXYZ23456789'; // Genera formato: XXXX-XXXX-XXXX // Verifica unicidad en administradores, profesores y alumnos // Máximo 10 intentos de generación para evitar colisiones

📝 9. Sistema de Auditoría (Event Logger)

El módulo eventLogger registra eventos críticos de seguridad:

  • auth.loginSuccess — Login exitoso con IP
  • auth.loginFailed — Intentos fallidos con razón
  • auth.passwordRecovery — Solicitudes de recuperación
  • auth.register — Registros nuevos

Comunicación Backend ↔ Frontend

Arquitectura REST API + WebSockets

🏗️ Stack Tecnológico

  • Backend: Node.js + Express.js (ES Modules)
  • Base de Datos: MySQL con mysql2/promise (pool de conexiones)
  • Frontend: HTML5/CSS3/JavaScript Vanilla (SPA dinámica)
  • Tiempo Real: Socket.IO para chat
  • Emails: Nodemailer con templates HTML
  • Deployment: Railway (PaaS)

🔄 Patrón de Comunicación

El frontend consume una REST API organizada en módulos:

// Todas las rutas protegidas usan verificarToken como middleware app.use("/api/auth", authRoutes); // Público app.use("/api/alumnos", verificarToken, alumnosRoutes); // Protegido app.use("/api/profesores", verificarToken, profesoresRoutes); app.use("/api/cursos", verificarToken, cursosRoutes); app.use("/api/pagos", verificarToken, pagosRoutes); app.use("/api/classroom", verificarToken, classroomRoutes); // ... 25+ módulos de rutas

📡 Flujo de una Petición Típica

Frontend (fetch) → Authorization: Bearer TOKEN → Express middleware → Route handler → MySQL query → JSON response
// Ejemplo: Cargar datos del alumno desde el frontend const response = await fetch(`${API_URL}/alumnos/${id_alumno}`, { headers: { 'Authorization': `Bearer ${localStorage.getItem('token')}`, 'Content-Type': 'application/json' } }); const data = await response.json();

Posibles Preguntas de Defensa

Preguntas frecuentes del tribunal y cómo responderlas

Tip: Hacé clic en cada pregunta para ver la respuesta sugerida. Respondé siempre de forma concisa, técnica y con ejemplos concretos del proyecto.

Arquitectura y Tecnología

¿Por qué eligieron Node.js como tecnología backend?

+
Node.js nos permite usar JavaScript tanto en frontend como en backend, lo que simplifica el desarrollo al mantener un solo lenguaje. Además, su modelo de I/O no bloqueante es ideal para manejar múltiples conexiones simultáneas, como el chat en tiempo real con Socket.IO. Express.js nos da un framework minimalista y flexible para construir la API REST.

¿Por qué MySQL y no MongoDB u otra base NoSQL?

+
El dominio del problema es altamente relacional: alumnos están inscritos en cursos, los cursos tienen profesores, las calificaciones dependen de inscripciones, los pagos se vinculan a alumnos y cursos. Una base de datos relacional como MySQL garantiza integridad referencial con foreign keys, soporta transacciones ACID (como en el registro de usuarios), y nos permite hacer JOINs complejos para obtener datos consolidados de forma eficiente.

¿Cómo funciona el patrón SPA que implementaron?

+
Los dashboards funcionan como Single Page Applications (SPA) sin framework. Cada botón del sidebar ejecuta una función JavaScript que: 1) hace fetch a la API REST, 2) recibe datos en JSON, 3) genera el HTML dinámicamente con template literals, y 4) lo inyecta en el contenedor mainContent. Esto evita recargas de página completas, brindando una experiencia más fluida. Usamos classList para animaciones de transición entre secciones.

¿Cómo se despliega la aplicación en producción?

+
Usamos Railway como plataforma de deployment. Railway detecta automáticamente el entorno Node.js, ejecuta npm start que corre server.js. Las variables de entorno (JWT_SECRET, credenciales de BD, etc.) se configuran en el dashboard de Railway. La base de datos MySQL también está hosteada en Railway, con las variables MYSQL* configuradas automáticamente. El frontend es servido como archivos estáticos por Express.

Seguridad

¿Cómo protegen las contraseñas de los usuarios?

+
Las contraseñas se hashean con bcrypt usando un salt de 10 rounds. Nunca almacenamos contraseñas en texto plano en producción. La función isBcrypt() verifica que el hash almacenado comience con $2, que es el prefijo estándar de bcrypt. En desarrollo existe una variable ALLOW_PLAINTEXT_LOGIN que nunca se activa en producción (isProd la bloquea).

¿Cómo previenen inyecciones SQL?

+
Usamos queries parametrizadas en todas las consultas a MySQL. La librería mysql2 utiliza prepared statements donde los valores se pasan como parámetros separados: pool.query("SELECT * FROM usuarios WHERE username = ?", [username]). Esto garantiza que los valores nunca se interpretan como código SQL. Además, express-validator sanitiza y valida todos los inputs antes de que lleguen a las queries.

¿Qué pasa si un token JWT expira?

+
Cuando un token expira, el middleware verificarToken captura el error TokenExpiredError y responde con un status 401 y el flag expired: true. En el frontend, cada dashboard verifica al cargar si existe un token en localStorage; si no existe, redirige automáticamente a login.html?session=expired. Los tokens tienen un tiempo de vida de 24 horas por defecto, configurable via JWT_EXPIRES_IN.

¿Cómo implementaron el sistema de roles?

+
Hay tres roles: administrador, profesor y alumno. Se almacenan en la tabla perfiles (id_perfil: 1=admin, 2=profesor, 3=alumno). Al hacer login, el rol se incluye en el JWT. El middleware verificarRol(...roles) actúa como segundo middleware después de verificarToken, verificando que el rol del token esté dentro de los roles permitidos. Cada dashboard (admin, profesor, alumno) es un archivo HTML separado que carga solo las funciones correspondientes al rol.

¿Cómo protegen contra ataques XSS?

+
Usamos Helmet.js que configura la Content Security Policy (CSP), limitando de dónde se pueden cargar scripts y estilos. Solo se permiten CDNs específicos (unpkg, jsdelivr, cdnjs). Además, objectSrc está configurado como 'none' para bloquear plugins, y frameSrc como 'none' para prevenir clickjacking. Los datos del usuario se insertan en el DOM como textContent cuando es posible, y la validación de inputs con express-validator sanitiza los datos antes del procesamiento.

¿Qué es el sistema CemiKey y para qué sirve?

+
CemiKey es un sistema de autenticación alternativo. Cada usuario (alumno, profesor o administrador) recibe una clave única en formato XXXX-XXXX-XXXX, generada con caracteres no ambiguos (excluye 0, O, 1, I, L para evitar confusión visual). Permite acceder al sistema sin necesidad de recordar usuario y contraseña. El generador verifica unicidad en las tres tablas de roles antes de asignar una clave, con un máximo de 10 intentos para evitar loops infinitos.

Funcionalidad

¿Cómo funciona el registro de usuarios?

+
El registro requiere un Código CEMI válido (generado previamente por un administrador). Este código determina el rol del nuevo usuario (alumno o profesor). El proceso usa una transacción MySQL: 1) Crea registro en personas, 2) Crea usuario en usuarios con contraseña hasheada, 3) Genera CemiKey única, 4) Crea entrada en la tabla del rol (alumnos o profesores) con legajo auto-incrementado, 5) Marca el código CEMI como usado. Si cualquier paso falla, se ejecuta ROLLBACK para mantener la integridad.

¿Cómo funciona el chat en tiempo real?

+
Usamos Socket.IO sobre HTTP. El servidor crea una instancia de ChatServer que maneja conexiones WebSocket. Los usuarios (alumnos/profesores) usan UserChatManager y los administradores usan AdminChatManager. Los mensajes se persisten en MySQL (chat_conversaciones y chat_mensajes) y se transmiten en tiempo real. Las conversaciones tienen estados (pendiente, activa, cerrada, resuelta) y soportan notificaciones push del navegador.

¿El sistema cumple con normativas de protección de datos?

+
Sí, implementamos funcionalidades alineadas con el GDPR: derecho a exportar datos personales (en formatos JSON, CSV o PDF), derecho a solicitar eliminación de cuenta, sistema de cookies configurables con banner informativo, política de privacidad detallada, y un sistema de referencias para seguimiento de solicitudes. Cada solicitud genera emails automáticos tanto al usuario como al administrador.

¿Cómo manejan los errores del servidor?

+
Todas las rutas usan bloques try/catch que capturan errores y devuelven respuestas JSON estructuradas con { success: false, message: "..." }. Se usa Morgan para logging HTTP (formato 'dev' en desarrollo, 'combined' en producción). El eventLogger registra eventos de seguridad. En el frontend, cada fetch tiene manejo de errores que muestra mensajes amigables al usuario usando SweetAlert2.

¿Qué mejoras implementarían a futuro?

+
1) Migrar a un framework frontend como React o Vue para mejor mantenimiento. 2) Implementar refresh tokens para renovar JWTs sin re-login. 3) Agregar autenticación de dos factores (2FA) funcional con TOTP. 4) Implementar un sistema de backups automáticos programados. 5) Agregar tests unitarios y de integración con Jest. 6) Implementar CI/CD con GitHub Actions. 7) Agregar un dashboard de métricas y monitoreo en tiempo real.

¿Cómo manejaron el trabajo en equipo y la organización?

+
Usamos Git para control de versiones y GitHub como repositorio remoto. El equipo se dividió entre frontend y backend, con un jefe de proyecto coordinando las entregas. Implementamos un flujo de trabajo con branches por funcionalidad y merges controlados. La comunicación fue constante para asegurar que la API cumpliera con las necesidades del frontend.

¿Qué es el sistema de Classroom y cómo se relaciona con el Dashboard?

+
El Classroom es el aula virtual donde se gestiona el contenido académico diario: tareas, entregas, anuncios, recursos, foros de discusión, y chat por curso. El Dashboard es el panel administrativo-académico que gestiona datos estructurales: inscripciones, calificaciones, asistencias, pagos. Ambos comparten las mismas credenciales de usuario (tabla usuarios), y se puede acceder desde uno al otro con un botón directo en el sidebar. Tienen login separado por diseño: el Dashboard usa /api/auth/login y el Classroom usa /api/auth/classroom-login, aunque ambos generan tokens JWT válidos.
